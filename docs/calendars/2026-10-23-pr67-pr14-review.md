# Review: bdobb #67 + openbq-docker #14 (exchange calendar, release/v4)

Verdict: the core operations are correct. The wiring is the problem: every path except `fetchWidgetData` quietly falls back to weekdays, and several boundaries are not built (PR #67's evidence doc admits most). Not mergeable as "Project 1".

## 1. Findings

### Critical
- **C1 Silent weekday substitution in preview, forms and tables.** `src/hooks/useTradingCalendar.ts:116` returns no exchanges for a bound widget, so `calendars` is empty. Every other `wireParams` caller then hits `dateExpressions.ts:573` (`ctx.calendar ?? weekdayCalendar(...)`). Callers: ParamControls:257/320, ParamEchoRenderer:30, WidgetCard:879, SsrmTableRenderer:53, rust/providerFactory:41, dataClient:529/750, useWidgetData:461. Example: XHKG-bound `T-1bd` the day after a HK holiday: the GET sends the XHKG date; preview, forms and SSRM send the weekday date. **Fix:** resolve once per batch and pass `resolvedCalendarValues` to every `wireParams` caller; with no resolution, fail.

### Important
- **I1 Precedence ignored.** `calendars/widget.ts:14` applies `widget.calendarBinding` to every field. It ignores `param.exchange` and the dashboard exchange, so a param set to XHKG on an XLON widget resolves on XLON. **Fix:** a binding precedence of param, then widget, then dashboard, with the legacy XNYS default shown in provenance.
- **I2 Fixed ±1-year fetch window.** `provider.ts:25` always requests `[UTC year−1, year+1]`. `T-2y`, `T-5y` and early-year `T-300bd` all fail with COVERAGE_UNAVAILABLE even though the provider can serve 20 years. **Fix:** work out the window from the parsed offsets, capped at LIMITS.days.
- **I3 The cache never hits and has no scope.** `dataClient.ts:465` builds a new provider, and so a new `CalendarCache`, on every fetch. `provider.ts:16` also passes `revalidate=!r.revision`, and no caller ever pins a revision. Each poll re-downloads about 3 years per calendar; offline cannot work; preview and run may see different bundles. The key is `backend.id` with no auth scope, and `clear()` is never connected to credential changes. **Fix:** one module-level cache keyed by backend, auth scope, calendar, revision, range and policy; pin the revision for the run; clear on credential change.
- **I4 Strictness looks inverted.** `operations.ts:15` (and `resolver.ts:22`) treats `authority_confirmed` as provisional, so operational mode rejects a confirmed closure but accepts `library_baseline`. **Fix:** the spec doesn't say which way round is intended, so ask; then fix the code and the test that locks the current behaviour in.
- **I5 Provider memory and CPU have no bound.** `calendar_v1.py:15` holds up to 256 cached bundles of as much as 20 years each, keyed by the raw `start`/`end` strings. Changing `start` by one day forces a fresh multi-year build and fills the cache (GBs in the worst case). `capabilities()` (line 20) calls `xc.get_calendar` synchronously on the event loop. **Fix:** normalize and align ranges to whole years, cap total bytes, run discovery in a thread or cache it.
- **I6 Unqualified calendars are exposed.** `registry.py:4` advertises XTSE, XETR, XLON, XTKS, XASX and XTAE with no conformance fixtures, and the capability start dates are hard-coded rather than taken from the supplier. **Fix:** list only fixture-qualified calendars and report the supplier's real bounds.
- **I7 Failures are opaque.** When resolution fails, `calendarResolution` stays `[]` (dataClient:472 only sets it on success), and nothing in the UI reads it. Users get an error string with no source, revision or coverage.

### Minor
- `resolver.ts:17`: joint composite is O(n²·k) via `days.find`; use the maps.
- `resolver.ts:30`: revision equals digest; the spec keeps them distinct.
- Client never enforces `LIMITS.bytes`.
- `bd` step limit sums signed offsets; sum absolute values.

### Tests that prove little
- `provider.test.ts` "revalidates live requests" locks in the cache that never hits.
- `operations.test.ts` locks in I4.
- `transport.test.ts`: the second test uses a bare `.rejects.toThrow()`, which any error satisfies.
- `test_calendar_v1.py:30` checks a hard-coded literal against itself.
- `test_calendar_core.py:51` is named for "unknown coverage" but never tests it.
- `scripts/vendor-calendar-contract.test.mjs` is excluded from vitest and appears in no script, so it never runs.
- XHKG/XTAI fixtures unused client-side; no hook tests for cancellation or cache leakage.

## 2. Spec gaps
- **B1 partial.** One supplier with a source digest, but `legacy.py` is still a separate generator. Security Master is absent on od v4; say so in the evidence.
- **B2 met** in shape. The client never calls `list()`.
- **B3 not met.** See I3. There are no packaged offline bundles.
- **B4 not met.** "Param override wins over widget, then dashboard" is not implemented (I1). A symbol param's exchange is never consulted: `program.symbol` is never filled, and no symbol-to-exchange lookup exists. TemporalDB, `dateFilters.ts` and `sourceAdapter` are not wired.
- **B5 not met.** The six-MIC menu remains and there is no capability-backed selection. Widget JSON is the only way in.
- **B6 not met.** Preview and run differ (C1); no receipt UI.
- **Gates.** 1 untested on the client. 2 and 3 partly met (no DST or overnight fixture). 4 fails (C1, I1). 5 met in operations.ts. 6 has no India/DFM/Eid fixtures. 7 has no session diff. 8 partly met (no offline, auth-change or oversize tests). 9 fails: the full host pytest does not collect, there is no container or installed-route check, no browser test, and no rollback document.

## 3. Style
- In `dataClient.ts:1-2` and `dateExpressions.ts:1-2`, imports sit above the license header.
- All the new TypeScript is dense one-liners with one-space indents and no doc comments. The repo uses formatted, heavily commented code (`params.ts`, `calendar.ts`).
- `useWidgetData.ts:127` uses an inline `import()` type where the file elsewhere uses top-level imports.
- Python: one-space indents (`test_calendar_v1.py`), semicolon chains, missing blank lines in `legacy.py`, stale "six client MICs" comment.
