# Matched desktop executor benchmark

Matched production worker measurements show Rust generally slower for cold load, sort/filter and pulled export. These results do not establish an overall speedup. Some warm pivot edits improved: the 20,000-row WebKit pivot-change median fell from 84.50 ms with TypeScript to 71.50 ms with Rust. Mixed-value comparisons remain blocked by ordering instability, and desktop measurements do not establish UI or regular-iPad acceptance.

Run `node scripts/benchmark-matched-executors.mjs` from the repository root. The separate `matched-executors.json` report preserves the historical `measurements.json` and compares the production-built real `createTableProvider` TypeScript and Rust Web Worker paths. Both include common client validation and cloning, worker messaging, response validation, and their actual calculation/conversion costs. Neither uses a synchronous calculation timing as an executor comparison.

The default run uses Chromium and WebKit, three discarded paired warmups and twenty recorded paired samples, with alternating engine order and sequential execution. Each observation has a 120-second driver deadline (configurable with `--timeout-ms`, bounded at 1–300 seconds). A timeout rejects the report rather than silently dropping a sample. Inputs are identical: 100-row, 10,000-row and 20,000-row grouped datasets; 10,000 raw rows; a 2,000-row wide split; fiscal calendars; and source/aggregate formulas. Frozen fixtures are reused without regeneration. Scaled rows receive distinct top-level values records for both engines. The larger case is a representative desktop workload, not a proposed iPad ceiling.

The driver sends the lossless tagged WireValue tree as one JSON string, parsed before the harness starts its timer. An exact JSON roundtrip check precedes dispatch. This removes measurement-driver object-serialization overhead, not product executor work. Earlier incomplete collections using object arguments were discarded; only the final complete collection is published.

Both the original 12-row and scaled 1,000-row mixed workloads remain explicit diagnostics with no accepted comparative timings. Isolated original-fixture probes passed both browsers, but the full collection rejected Chromium original12 during sort/filter and scaled1000 during cold load. WebKit original12 observations are retained as exploratory only. See `mixed-parity-diagnostic.json` and the full report. A later preflight pass does not unblock either known unstable comparison. No runtime fix or relaxed parity is included.

Parity is a preflight for each case, not a claim that every timed observation receives independent parity checking. Before any timing for a case, both engines must pass each cold-load and edited view against an independent `calculateView` baseline and cross-engine view, first block, totals, and full export parity. Rows include IDs, order, values, errors and formats. Columns and full export metadata are also compared between engines. Only request IDs, transfer IDs and transport batch counts are excluded from cross-engine comparison; batch counts remain observations. Baseline row projection uses the published column IDs, matching the contract of presented output. Baseline comparisons also verify columns and total values. Numeric tolerance is restricted to explicit output IDs published with mean aggregation or aggregate division formulas, and only row or total value positions; the bound is `max(1e-12, 1e-12 * max(abs(actual), abs(expected)))`. Source fields, sum values, metadata, errors, formats, and signed zero remain exact.

Each observation owns a fresh executor and worker. The browser HTTP cache is warm; these are worker-cold loads, not cold network loads. Boundaries record factory creation, acquisition including worker startup and input conversion, initial apply, sequential first block of up to 100 rows, totals, and their combined cold-load-ready time. The acquisition API does not independently expose worker startup versus input conversion; their combined boundary is explicitly labeled. Warm pivot and sort/filter actions restore the initial definition outside the timed window before measuring apply and first-block/totals readiness. Full export restores the initial definition and drains every pulled batch. Parity work is outside recorded timing windows. Each metric includes median, nearest-rank p95 and individual chronological observations; complete paired observations retain engine order.

Source hashes, workload hashes, Wasm hash, protocol version, toolchain, platform, browser version, locale and user agent are recorded. Browser worker allocator/process memory peaks and UI paint are not measured. A shared renderer benchmark, physical regular-iPad acceptance, and any default activation decision remain separate future gates. TypeScript remains the default.

## Scaled mixed ordering finding

Reproduce the bounded original-versus-scaled probe with `node scripts/benchmark-matched-executors.mjs --workloads mixedOriginal,mixed --parity-only --output /private/tmp/mixed-parity.json`. The original dataset has 12 rows; scaling repeats those values into 1,000 rows with distinct row IDs and top-level values records. The initial definition has no grouping, splits on `dimension`, and sums `revenue`. The pivot-change action groups `dimension` and removes the split.

The saved diagnostic found Chromium Rust's initial split column at index 1 had ID `["number","-Infinity"]\u001fsum`, while the independently calculated baseline expected `["number",0]\u001fsum`. A preceding run also rejected Chromium TypeScript's grouped pivot export: the first `groupPath[0].memberKey` was `["number",0]` versus baseline `["number","-Infinity"]`. Both isolated original-fixture browser probes passed; scaled WebKit's probe passed. The later full collection rejected Chromium original12 TypeScript versus baseline during sort/filter: split column index 1 was negative infinity versus zero. Scaled1000 TypeScript also failed at cold load with that column mismatch. These observations establish unstable mixed comparisons in both sizes, without establishing a runtime fix.

The existing comparator in `src/lib/pivotTable.ts:101–106` subtracts values for number/number pairs and otherwise compares their string representations through `Intl.Collator`; `partition` sorts those mixed group keys at line 212. Numeric, string, BigInt, NaN and infinity keys can have inconsistent pairwise ordering. That is a plausible explanation for the differing results across paths, browsers and reproductions; the benchmark does not claim that hypothesis has been proved. Failed and known unstable comparisons publish no timings.

The collection completed in 398.75 seconds and intentionally returned status 1 with a partial report. Fourteen nonmixed browser/workload cases passed preflight and each retained twenty paired observations. The report records the exact measured driver hash and its source in `matched-executors-measured-driver-source.json`. Post-collection classification blocks both mixed names from accepted comparisons; any retained WebKit original12 observations are exploratory. `postCollectionClassification` records that rule and the future driver hash. The harness, utility, workload and Wasm hashes describe the actual measured paths. Future default runs conservatively block comparative timings for both mixed names.

## Collector corrections and strict revalidation

Independent review found three reusable-collector defects after the saved collection: a deadline could leave its old evaluation running while later cases started; a fixed-port health response could belong to a different server; and the numeric-tolerance guard matched trailing keys inside nested metadata or raw objects. The saved workloads do not contain the affected nested shapes, and no timeout or server collision was observed. The original 560 accepted executor observations and their statistics remain unchanged.

The corrected driver owns its server through a random health-header token and checks child liveness. A coded timeout or fatal child exit closes the browser context and abandons every remaining case on that page. Aborted or incomplete collections return a partial report and nonzero exit, including when no case-specific failure exists. Git status now supplies working-tree provenance. Focused tests exercise stalled active work, unrelated healthy servers, a real occupied-port child failure, child death, aborted status and missing requested browsers/cases.

Tolerance now matches exact baseline or snapshot schema roots, with output IDs specific to each action. Nested metadata and raw cell objects compare exactly. All fourteen nonmixed Chromium/WebKit cases passed a fresh owned-server [strict parity-only revalidation](matched-executors-revalidation.json), taking 59.693 seconds. It collected no replacement timing observations or warmups; its samples/warmups configuration fields do not assert twenty independent parity trials. The source archive retains both the exact measured and revalidated driver/helper versions; `postCollectionCorrections` records current hashes, stricter gate results, and the subsequent status-only correction. UI paint, memory and device gates remain unmeasured.
