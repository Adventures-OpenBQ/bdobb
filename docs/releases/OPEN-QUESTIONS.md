## Future decision (not v10): DuckLake for fundamentals/holdings/transactions

Recorded 2026-10-12 with the user's v10 rulings (openbq-docker ledger, "Crash recovery and the S3 tier", ruling 4: keep Delta Lake). Not a v10 item; nothing on either branch changes for it.

- **Delta stays for ticks in v10.** eod-dump writes Delta (delta-rs) to RustFS and live-grid reads it back.
- **Proposal:** bring in DuckLake, with a **PostgreSQL catalog**, when the first bitemporal tables land (holdings, transactions, fundamentals): Episode 11 or later.
- **Design explicit effective-time and knowledge-time columns** in those tables. A table format's time travel is storage time (when a snapshot was committed), not knowledge time (when a fact became known) and not effective time, so neither Delta's versions nor DuckLake's snapshots can stand in for bitemporality.
- **Costs to accept first:** a PostgreSQL catalog service to run; a backup that covers the bucket **and** the catalog together; no snapshot spanning Delta and DuckLake, so a run that reads both must pin both (a Delta version and a DuckLake snapshot); DuckLake's global `data_path`, which forces two catalogs if the store is tiered (hot/cold); and snapshot expiry that nothing guards, so an expiry can remove what a pinned run still needs.
- **Revisit whether ticks follow.** The donor's ep15 spike (2026-09-23) measured DuckLake point-in-time reads at 0.87-1.00x Delta's, so performance alone does not argue for moving ticks; decide with the bitemporal tables in hand.
