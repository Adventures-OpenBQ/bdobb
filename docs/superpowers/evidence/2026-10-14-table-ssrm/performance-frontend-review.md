## Actual call paths and bounds

Managed: DashboardGrid → TableExecutionRuntime → store.acquireDashboard/syncDashboard → ensure → managedProvider.open → remote transport → authenticated createManagedTableRequest → web relay → canonical gateway → native service. ensure applies a snapshot model; useTableResult then requests rows and totals concurrently and publishes only a matching joined revision. Its row cache has 12 blocks × at most 100 rows and an instance-local in-flight map. Concurrent same-key row requests and cache hits are already suppressed. It preserves old completed rows while a new model/rows/totals publication is pending. Do not replace this with loaded-page calculation or early incomplete publication.

Managed linked table: ensure(parent) → parent.managed.deriveLinked → child session → child applyModel; all derivation stays server-side, avoiding a browser full-input transfer. Existing derived-session leases preserve admitted chart/export consumers when a session is retired. Linked chart: source executor.chartData → managed POST commands → projected full result → buildLinkedFigure → Plotly. Export: managed presented POST starts a pinned export, GETs sequential batches, DELETE closes; collectPresentedExport accumulates all batches then creates export rows and output bytes.

LIVE: SsrmTableRenderer.LiveTable creates provider/session for identity (including definition), applyModel reads/discovers a real upstream page, then renderer calls rows(offset0,100), which fetches the same page again. Later navigation always fetches. LIVE has ephemeral row identities, explicitly denies snapshot-only full-scope consumers, and should retain those semantics.

## Ranked findings

### 1. Avoid full-scope chart refetches for chart type/display-only changes; avoid building every delivered figure twice

Locations: `src/components/renderers/LinkedChartRenderer.tsx:32`, `:71–89`; `src/lib/widgetData/chartFigure.ts:25–56`; managed request at `src/lib/tableExecution/remote/managedProvider.ts:142`.

Trigger: user changes Column→Bar/Line or Grouped→Stacked with unchanged parent result/category/measures. `mapping = JSON.stringify(settings)` is a data-loading effect dependency. It starts another full `chartData` command even though only the Plotly presentation changed. After every response, line74 constructs all trace arrays/hover strings to check `ok`, discards that figure, then the memo at88–89 constructs it again. Builder scans all projected rows per measure, creates ids, labels, numeric arrays, and per-point escaped hover strings. Cost scales with full presented output, not the 100-row UI block. Multiple charts with identical projections also have no executor-level shared request/cache, but cross-chart sharing is a larger optional extension.

Concrete optimization: separate acquisition key (parent executor/session/result identity + revision + validated field projection) from presentation mapping (type/display/etc). Reuse an already completed matching projected dataset for presentation-only changes; recompute the figure locally once. Preserve the exact completed dataset/mapping/revision atomic stale-delivery semantics and validate values exactly as buildLinkedFigure does now. A bounded shared in-flight/read cache could additionally serve identical projections; preserve per-consumer cancellation and retain leases until every admitted consumer finishes. Do not key only by a widget/revision that can collide after reopen or across owners.

Measured request-count proof: `/private/tmp/ssrm-chart-probe.cjs` uses actual bundled production LinkedChartRenderer, React, JSDOM and actual chartFigure code; substitutes stable store/theme/Plotly sink only, and instruments builder calls. Results: mount=1 chartData call/2 builds; type-only change=2 chartData calls/4 builds cumulative; display-only change=3 calls/6 builds cumulative. No HTTP traffic/timing or iPad claim. Reproduce `node /private/tmp/ssrm-chart-probe.cjs` (requires existing clone node_modules). Expected after optimization: 1 data acquisition across all three states; one figure build per completed presentation. Whole-result bytes avoided depend on admitted shape.

Target regression/benchmark: hold a chart response while source refresh/reopen, change mappings, switch theme, verify old results cannot publish as current; assert type/display changes issue zero new chart commands, field changes issue one, and all selected/off-page rows remain included. Profile production browser allocations/long tasks at existing 1,205×4 fixture and an admitted wide 20k-row synthetic shape, not an unsupported million-row claim.

### 2. Hand off LIVE apply's first page to rows instead of immediately fetching it a second time

Locations: `src/lib/tableExecution/remote/openbbSsrm.ts:166–180`, `:182–208`; `src/components/renderers/SsrmTableRenderer.tsx:59–62`.

Trigger: every initial LIVE table load and identity reset (sort/filter/pivot/reopen/refresh). Apply fetches the first page to validate schema/type/count, but Published stores only schema/query/path maps. Renderer immediately calls rows(offset0,100), which issues identical POST. With absent input columns and grouping/pivot, an additional ungrouped schema-discovery request precedes both, giving three serial requests.

Concrete optimization: retain a bounded, publication-owned first-page delivery and hand it off once to the exact matching first rows request (path/range/query/revision). Build group path maps and row identities through the same rows conversion/validation logic. Restrict reuse to the initial handoff; LIVE future refresh/page navigation still fetches new data with LIVE metadata and ephemeral row ids. Discard on superseding apply, abort/dispose or mismatched range. Do not introduce long-lived snapshot claims or route LIVE through the exact-count managed adapter. Declared input schema can eliminate discovery separately where manifests know it.

Measured provider proof: `/private/tmp/ssrm-request-count-probe.mjs` imports production openbbSsrm bundled as `/private/tmp/ssrm-openbb-perf-probe.mjs`. Fake fetch records exact request bodies and returns bounded synthetic pages. Flat declared schema: 1 apply POST, 2 POSTs before first visible rows. Grouped undeclared schema: 2 apply POSTs, 3 POSTs before rows. Final two JSON request bodies byte-identical in both. Reproduce `node /private/tmp/ssrm-request-count-probe.mjs`. This is request-count proof, not end-to-end latency measurement. Saving one serial upstream roundtrip and one page transfer/validation is predictable; absolute latency depends on deployment. Data cost is bounded to 100 rows here.

Regression: assert one POST for flat apply+first matching rows and two for undeclared grouping discovery+handoff; later same-page navigation must fetch, identities remain page-local, schema/type mismatch still refuses, and a held superseded response never seeds the new publication.

### 3. Stop eagerly acquiring every hidden tab's independent managed table/descendant

Locations: `src/stores/tableExecutionStore.ts:465`, `:550–552`, `:717–722`; publication fanout `:446–448`; linked derive `:312–321`, apply `:406`; `src/components/DashboardGrid.tsx:76` chooses visible tab while its TableExecutionRuntime receives the whole dashboard (`:81`,`:226`).

Observed in source: the store registers cards from all dashboard tabs and acquireDashboard invokes ensure for every node. Subsequent sync repeats ensure over every card when the dashboard has a lease or executor. On parent publication it eagerly ensures all pending/updating descendants. Thus invisible unrelated managed roots and linked tables still open sessions, apply full models, and retain server native result state. The 12×100 UI cache does not bound this cost. Existing qualification explicitly notes session quotas and large retained worker/result reservations; this can drive 429/resource refusals as well as waste compute. No local memory/concurrency measurement was made for hidden tabs.

Concrete optimization: keep metadata/graph validation global, but acquire/apply a demand closure from mounted visible tables/charts, export/authoring consumers, and their ancestors. Existing hidden completed results can become stale without immediately recalculating; on-demand ensure settles dependency chains. Separate activity leases from dashboard ownership, retain admitted full-scope consumers across retirement, and bound/expire inactive sessions without suppressing cancellation/TTL/limits. This is a larger lifecycle change, not a quick cache tweak.

Regression/benchmark: multi-tab dashboard with one visible managed table and five hidden independent roots/descendants; assert hidden independent cards send no open/apply/derive traffic before demand. Activate a hidden chart whose source lives on another tab and assert complete upstream closure/freshness. Refresh parent during a pinned export/chart, delete/rebind a source, close tab/dashboard, and verify no stale publication, premature disposal or admission leaks. Compare native reservations, startup HTTP counts and time-to-visible-ready, without increasing quotas.

### 4. Full export remains O(all rows) browser memory despite bounded remote batches

Locations: `src/lib/tableExecution/remote/managedProvider.ts:148–169`; `src/lib/export.ts:8–18`,`:75–101`,`:145–152`; `src/lib/tableExecution/subsetTransfer.ts:21–34`; `src/components/WidgetCard.tsx:1023–1033`.

Trigger: card CSV/JSON/XLSX export of a large admitted cached table. presented reads at most negotiated maxRows per batch (100 in qualified profile), but collectPresentedExport clones each decoded batch into an accumulating WidgetDataset. presentedForExport then creates another complete set of row records, followed by complete CSV/JSON strings or XLSX allocations. Bounded row transport is therefore not bounded browser export memory. Each batch also waits for the next HTTP request; 20k rows at100 implies 200 data exchanges, plus close (algebra, not measured capacity/latency). Managed linked derivation already avoids this browser export path and should continue to.

Concrete optimization: provide a dedicated streaming CSV/JSON export sink that validates sequence/identity/metadata and encodes bounded batches to a task-owned temporary file/blob chunks, then atomically finalizes only after the final batch. iOS already requires finishing the file before opening the picker, which is compatible with temp-file staging; do not show/save a successful partial file. Keep existing all-eligible ignoreSelection=true semantics, order, grouped labels, duplicate flattened headers, formulas-as-text CSV escaping, raw values/errors, finality and revision pinning. Header depth/group metadata may need to be supplied up front or a bounded first metadata pass; do not infer export schema from only the first data row. Keep XLSX on a separately measured path if the library necessarily materializes workbooks. A protocol to coalesce several individually bounded batches into one bounded response is a separate change, and must retain wire/row/admission/backpressure/cancel limits; simply raising limits is not the optimization.

Regression/benchmark: use actual menu export at off-page exclusion + grouping and parent refresh during admitted stream; compare exact bytes with current writer, no final file on truncation/cancel, temp cleanup, and memory high-water across row counts. Measure browser heap on actual WebKit/iPad. No peak-memory reduction was measured here.

### 5. Lower-priority bounded grouped-page render scan

Location: `src/components/renderers/SsrmTableRenderer.tsx:90`. The inner columns.map does `block.groups.find` for every cell although the group is row-specific and used only in the first column. For100 grouped rows×256 admitted columns, a matching-group linear scan performs about1,292,800 rowId comparisons per render (sum1..100 ×256); pending/page status updates render the table again. This is still bounded page work and usually lower value than chart full-result/network savings. Hoist to once per row or index groups by rowId once per block; keep exact same keyboard/group navigation. Count comparisons/render for a 100-row wide grouped page and verify only first-column buttons and group paths remain correct. Do not sell it as a full-table optimization.

## Secondary opportunities / guardrails

- `useTableResult.ts:49,59` is insertion-order/FIFO, not LRU: a cache hit does not promote a block. Backtracking over >12 pages can evict a just-revisited older block on the next insertion. A bounded path-aware LRU is a modest network win; measure a real scroll trace and retain the100×12 limit/in-flight bounds. Its current deduplication is already present, so do not claim duplicate requests on steady-state cache hits.
- Metadata hooks are independent for intentional cancellation isolation. `LocalTableRenderer.tsx:224` requests a page facet automatically and separate page/author metadata hooks can request the same category. A bounded shared immutable result cache keyed by full request+active session/revision can reduce repeat facet reads without sharing UI pending/error/cancel state. No exact duplicate-facet request probe was run.
- Relay buffering is intentional failure atomicity: web `server.mjs:278–285` bounds/validates a complete JSON body before responding; gateway `funnel-gateway/server.mjs:450–478` does the same, then reparses/reserializes via reply. Frontend `transport.ts:51–64` accumulates chunks and copies to one byte buffer before fatal UTF-8 decode/JSON parse, then managedProvider decodes inner wire. Avoid proposing unsafe pass-through streaming/removing JSON validation; request elimination above removes all these costs for eliminated calls. If profiling identifies encoding as material, gateway can forward already validated original bounded bytes instead of JSON.stringify(parsed), and transport can incrementally fatal-decode bounded chunks to reduce an extra full byte copy. Keep exact octet caps, UTF-8 checks, sanitized errors, no upstream header/cookie leakage, deadline/disconnect cancellation and all-or-error publication. These changes require targeted equivalence/security tests; no isolated relay heap/CPU benchmark was run.
- Managed apply computes envelope twice (`managedProvider.ts:124` preflight and `execute:96`). Reusing a prevalidated captured envelope saves duplicate definition traversal/encoding, while retaining preflight before revision consumption. Model definitions are typically smaller than result/chart payloads, so this ranks below the measured request/figure wins.
