## APIs and architecture

- `pivot-wasm` exports actual `open_session`, `dispatch`, `close_session`, and `protocol_version`. Versioned JSON envelopes carry protocol/session identity and typed operations; structural Wasm host options contain serialized session options plus a fallible ordering callback. `wire.rs` translates every operation and response to the native CoreRequest/CoreResponse variants. The exported generated TypeScript declaration includes the host option type. Sessions own native state and handles; close removes the state. There is a bounded 32-handle ceiling; the worker uses one session.
- `rust/runtime.ts` exposes typed `RustRuntime` methods and `loadRustRuntime`; `createRustExecutor(widgetId, factory?)` uses the existing worker client with `rust.worker.ts`. `protocol.ts` adapts the existing execution envelopes, tagged cell/metadata values, original ordered analytical recipe evidence, insertion-ordered runtime entries, exact counts and presentation field presence. It does no calculation. No Tauri/native API import, TypeScript Pivot/Statement calculation shim, fallback, provider/default change or renderer change was introduced.
- The worker initializes Wasm once, validates and queues at most 32 requests, emits protocol readiness, and serializes dispatch/acquisition. Supported files use the existing TypeScript `datasetFromBytes` parser inside the worker, then register the validated dataset with Rust. The typed registration contains neither the original file bytes nor file name. Direct low-level ImportFile calls map to the core's explicit acquisition refusal; UI imports are acquired before that seam.
- Register/apply/preview/bind/member/witness/selection/rows/facets/inspect/totals/chart/presented/next/cancel/dispose all map through native variants. Native transfer IDs, request IDs, revisions, sequences and exact counts map explicitly to existing responses. Cancel/dispose control acknowledgements are validated and consumed privately because the existing client uses fire-and-forget controls.
- Unicode-scalar descriptor preflight covers every string and key before structuredClone/JSON, including data, metadata, saved AST, recipe/fiscal evidence, runtime entries, identities and optional compact error fields. Valid surrogate pairs remain unchanged; lone UTF-16 units explicitly refuse. This deliberate protocol-1 compatibility limitation is preserved and documented in the design. Tagged missing/null/negative-zero/nonfinite/BigInt values remain lossless, including a cell named `tag` and a nested record whose user properties resemble tags. Floating saved literals and timestamps retain -0 in JSON; integer coordinates use canonical zero.
- Existing request validation retains the exact collection-specific inspection optional-field guards. Native direct-core optional-field validation was **not** consolidated: the Task 7 direct-core gap stays on the ledger. Worker/runtime wire preflight exercises those existing guards, including presence of an undefined forbidden group field.
- Response adaptation preserves generated optional undefined presentation fields, compact optional errors/formats and empty-map presence, original saved Statement authority, source metadata and model-warning evidence. InputSchema stays acquisition-only: it neither receives generated presentation column fields nor unsupported model-warning envelope fields. Error descriptors fit the existing client protocol while the original complete native/host Diagnostic is retained in the diagnostics envelope.

## Lifecycle and approved shared changes

Optional initialization hooks in workerClient preserve the existing TypeScript worker's initialization behavior. Ready protocol mismatch, loading failure, traps, message loss and malformed responses invalidate the generation, terminate the worker and settle every waiting initialization/request promise. Only validated ordinary request errors reject one request. Malformed error descriptors are fatal. Stale generation callbacks cannot publish schema/selection. Disposal rejects initialization even before any registration is posted.

Cancellation invalidates publication. Applying/registering/importing hard cancellation terminates the worker and later hydrates only the last committed input/model. No interruption inside synchronous Wasm dispatch is claimed. Trapped modules may also trap during close; cleanup is best effort and fatal notification is still emitted so the client can terminate the worker.

The controller explicitly approved the necessary narrow acquisition exception to the plan's hooks-only wording: workerClient now stages input/import state and commits it, together with clearing the old model, only after a validated successful registration. Failed/cancelled acquisitions reset the candidate generation and retain the committed source/model. Existing TypeScript-client regressions verify cancelled registration, invalid registration and failed import all restore the previous calculated totals; supersession tokens prevent an older acquisition from committing into a newer operation.

Two narrow native corrections were explicitly approved by the controller after real Wasm boundary evidence:

1. `validate_recipe_source` compares canonical typed serde_json::to_value results instead of serialized strings. The baseline recipe's JSON.stringify intentionally normalizes the sign of zero; actual typed AST -0 remains unchanged for calculation. Original ordered recipe serialization and graph/model guards stay unchanged, and a forged nonzero literal still refuses. This is zero-sign recipe equivalence, not a general numeric/string approximation.
2. CachedOrder scalar comparisons call/cache `host.compare` separately from raw comparisons calling/caching `host.compare_raw`. Mode-tagged keys share the **same combined entry bound**; failures are never cached. Successful raw Unordered remains distinct from a Diagnostic and scalar ties. This restores independent scalar/raw fallibility rather than accidentally bypassing the scalar callback through the raw callback. Task 12 should account for the mode tag and callback/cache/conversion costs; the entry ceiling did not increase.

## Task 8 review fix round 1 — acquisition ownership during readiness

Base: 9faaf5987836185a9d9290937900cece97495f98. Read task-8-review.md in full and verified its one Important finding against the client call path before changing code. Review-reception and TDD skills applied; no subagents/reviewers. The race is real: `ensure` can be awaiting readiness with no posted request, so `pending.size` does not represent a candidate acquisition. A model apply can then supersede its operation token while sharing its hydration. The obsolete acquisition rejects without restoring the worker's input, or a model against the discarded input can succeed.

The minimal shared-client change tracks an acquisition operation owner across readiness and hydration. A superseding apply resets that candidate generation before `ensure` re-registers the last committed source. Reset clears the owner immediately; acquisition catch/finally require that same current owner, and catch also requires the current operation token. Thus old acquisition cleanup cannot reset a replacement generation or clear a newer acquisition owner, including recovery begun before the old catch executes with no intervening new operation token. Successful/failed/cancelled/disposed/superseded settlements release the owner. Public APIs, protocol, codecs, calculations and TypeScript default choice are unchanged.
